# 从新建项目到阶段科研成果：完整用户旅程

状态：产品设计，PLANNED。以下描述期望的完整体验，不表示现有版本已经支持这些界面与自动衔接。
当前五角色的开发方案见 [实施计划](RESEARCH_ASSISTANT_PLAN.md) 与 [Prompt 包](RESEARCH_ASSISTANT_PROMPTS.md)。
“经过一段时间得到成果”是工作流目标，不承诺在指定时间证明开放问题或得到可发表结论。

## 1. 新建项目

用户点击“新建研究项目”，填写名称，用自然语言说明研究方向，可选择本地保存位置。
默认本地、私有；GitHub、文献服务和后台执行设置可以稍后配置，不要求同时完成所有配置。
系统创建独立研究工作区，保存项目说明、会话、材料目录及配置，不把研究资产混入引擎源代码。
研究入口确认当前模型连接是否可用；未连接也允许导入、查看和整理已有材料。
密钥通过既有获准配置或专用连接界面使用，不要求用户把密钥贴进聊天记录。

用户看到：项目卡、当前目标、材料入口、模型连接状态、预算状态和下一步。
项目创建本身不意味着启动模型、授权付费研究或建立远程仓库。

## 2. 描述方向与现有基础

用户可以给出精确命题，也可以只说“我想研究某类球对称解的质量与能量关系”。
研究入口先区分研究方向、候选问题和可执行任务，询问最影响下一步的内容：
目前有什么材料、希望先证明/计算/探索什么、已知哪些结论、有哪些明确限制。
用户不需要一开始就知道全部引理和验收细节。

系统保存项目简述和待澄清问题。对宽泛方向先提出几个有出处的候选切入点，
不把模型提出的选题声称为已确认的开放问题或创新点。

## 3. 导入旧材料

用户添加笔记、证明、论文或计算档案。系统说明支持的格式、处理状态和失败原因。
当前 Intake v1 的文本/Markdown/LaTeX 是已有基础；PDF/OCR 等需要额外实现，不能假装已经支持。
材料与 Intake 角色保存原件、版本和出处，识别文献、已有论证、定义、数据和计算结果。
无法可靠识别的公式明确标记并请求局部核对，不让用户重新整理整份材料。

用户看到：哪些材料已读入、哪些尚未解析、哪些看起来重复、哪些条件发生冲突。
旧证明保留原始状态；“文件导入成功”“转述准确”和“证明成立”分别记录。

## 4. 建立项目研究地图

系统建议项目内的研究问题及其关系：已知基线、主问题、支撑问题、可选路线和验证任务。
项目级规划需要用户采用；模型建议的引理和路线首先保持候选，不自动成为已成立依赖。
简单项目可以只有一个问题，不强制用户绘制复杂研究图。

Hawking 质量题适合作为基线：先验证约定、质量恒等式和计算工具的正确衔接。
更长期问题应由用户实际研究方向决定，不从这道恒等式自动推断一个新的科研命题。
地图显示“为什么这一步值得先做”，并区分复现、校准与可能的新研究结果。

## 5. 生成并修订第一份任务书

Intake 提供目标、条件、定义、已有依据、缺口和验收条件的简洁预览。
用户可以说“去掉这个条件”“这一段还是猜测”“采用我的符号”“约定你来定”。
系统将自然语言修改落实为新版本，突出数学含义变化，保留原文和历史版本。
用户已决定的事项不重复追问。

对于当前实际案例，用户原题未给出三个方程；用户回复“你自己定”后，
系统选择一致的双零度规与标量场归一化，并明确说明选择来自模型、已获本次范围内授权。
这不授予后续付费执行或公开发布权限。

## 6. 采用任务并建档

用户说“采用这版”，建档角色生成精确版本的合同，程序登记必要对象并核对引用。
如有多个同名结论、已失效依赖或会阻碍求解的未决条件，集中解释具体问题。
用户无需编写 YAML、分配节点 ID 或复制文件到正确目录。

系统返回任务卡：目标和条件、输入材料、验证要求、已登记版本及是否具备执行条件。
采用后的修改通过版本和影响检查处理，不覆盖原记录，也不将采用合同记成证明确认。

## 7. 选择执行方式与授权预算

运行管家先列出可执行方案，例如“先做推导和代数核对，再根据结果讨论延伸”。
用户选择单次任务或在指定时段/预算内持续推进；授权绑定项目、目标版本、工作区、
允许的模型/工具/在线服务、调用及时间限额。界面区分可强制限制与仅能估算或事后核对的费用。
预算由上限控制，不由角色自行增加；供应商无法硬限制费用时如实说明。

“按这版开始，使用已设定预算”可一次覆盖采用和运行，不要求分别点许多确认。
只有授权缺失、超限、重大目标变化或超出允许工具/数据范围时才再次请用户决定。
授权范围内的角色切换、检查点保存和获准的局部工具操作自动衔接。

## 8. 执行第一轮研究

派发前，程序检查核心命题、假设、相关引理和材料是否实际进入模型输入。
缺失的必需材料先处理；用户可以展开查看上下文清单，不必亲自拼装提示词。
单核心模型执行研究，按需要使用会话内策略和允许工具。执行器保留语义进度、
候选推导、失败记录、工具回执、消耗和检查点。

Hawking 质量基线的实际交付应包括两个方向的质量求导、方程代入、逐项抵消及符号检查。
不能根据题名返回固定答案；未实际执行的检查不能显示“通过”。
界面区分“模型正在运行”“最后已记录到某一步”“检查工具正在执行”。

## 9. 用户离开期间

用户可以关闭页面，但必须能看清后台服务是否仍在运行。
只有实际存活的工作者、有效授权和可用资源才能继续；电脑睡眠、断电或服务退出后不声称继续研究。
后台运行能力需要真实实现和生命周期管理，不能依靠聊天中的承诺。

系统在授权内保存检查点，并在有实质成果、需要决定、预算耗尽或执行失败时通知。
默认不发送密集“还在运行”消息；通知渠道由用户选择，不擅自发送邮件或联系协作者。
跨项目模型调用也须遵守统一的单核心执行边界，避免多个项目各自占满相同资源或预算。

## 10. 查看进度与处理中断

用户问“做到哪了”，系统回答本轮新增了什么、仍卡在哪里、花了多少、下一步是什么。
进展不能只用对话长度、运行时间或 Agent 调用次数衡量。
应区分新候选推导、独立检验通过的结果、得到依据的反例、排除的路线和未完成步骤。

失败分为数学障碍、上下文缺失、工具不支持、服务/网络异常及预算限制。
不同原因给不同恢复动作，不一律换 Prompt 重试。
调用结果不明时先核对真实进程、请求 ID 和回执，不自动重发可能已计费的请求。
用户说“暂停”后显示请求状态，实际保存并停止到边界后才显示“已暂停”。

## 11. 修改方向与继续研究

用户可以说“放宽这个条件”“先研究这条引理”“旧论文中还有一个更强版本”。
系统显示哪些任务、证据和已得结论受到影响，保留原路线和版本。
进行中的调用在适当边界暂停或结束；不把新条件静默塞进旧任务并混用旧结果。
版本变化后重新检查原授权是否覆盖新目标，不因重建任务而偷偷重置预算。

用户回到旧路线时，应能恢复其数学状态、适用条件、未决义务和相应证据，
不要求重新解释几周前的研究过程。

## 12. 按研究周期整理进展

单轮研究结束后，结果角色整理本轮变化，项目规划能力更新后续建议。
示例节奏：第一周期复现和校准，第二周期围绕一个核心障碍推进，之后根据实际证据调整。
周期可以按用户指定的天数或有效研究预算划分，不承诺某周必有定理。

系统给出短周期报告：新增结果及状态、假设变化、失败路线、主要阻碍、成本和下一轮选项。
用户选定优先级后，既有调度器负责授权范围内的执行，不由规划角色随意启动新课题。
达到预先设定的停滞阈值时提出换路线、补文献、缩小目标或暂停的建议，避免无限消耗。

## 13. 补充文献与评估新颖性

在已授权的来源和访问范围内，文献能力检索、去重并定位相关陈述，绑定具体版本与位置。
需要全文时准确区分已拿到全文、只有元数据、只看过摘要等状态。
新文献可能引入适用条件冲突或使先前“可能新颖”的判断失效，更新相关任务的复核状态。

模型给出“目前检索范围内未发现相同结果”，不能据此断言全球首次。
论文中已有的质量恒等式应标为基线复现，不作为本项目原创成果。
未经授权不购买文献、不上传私人材料到新服务、不联系论文作者。

## 14. 提炼候选科研成果

经过若干周期，项目可能得到候选定理、反例、可重现计算方法、数值现象、
带明确条件的局部结果或可追溯的失败路线。每种成果都有适用范围和状态。
结果角色提出精确成果陈述，逐项链接所用假设、依赖和支持记录。
条件性结果必须把条件写进陈述，不能在总结或论文中抹去缺口。

用户看到成果清单，而不是只有一份很长的聊天摘要。
如果没有新的科研结论，明确说明目前只有基线复现、工具建设或未决研究，不承诺包装成论文。

## 15. 验证与成果验收

系统列出每项候选成果需要的验证：计算重演、证明义务、可用形式化工具或人工核对。
已安装且获准的确定性工具可在预算内执行。工具不覆盖的数学推理明确保留待核对状态。
不启动独立 AI 审查 Agent；同一核心模型的自检不能变成独立审查记录。

用户可以提供人工审阅意见，系统保留原始记录、核对范围及来源声明；不能只输入一个标签就认证身份。
一项代数检查通过只支持对应恒等式，不自动验证整个长期研究项目。
验收后的成果也绑定版本，未来假设或依赖变化时能够提示其适用性变化。

## 16. 生成可交付成果包

用户说“整理成阶段报告”或“准备论文草稿”，系统从当前成果和证据记录生成：

- 精确问题与假设、主结果、完整论证或计算方法。
- 证据状态、未解决义务、适用范围和局限。
- 可重演的代码、输入数据、工具版本与执行记录。
- 带具体位置的参考文献，以及创新性判断的检索范围和日期。
- 所用合同、材料、检查点和成果版本的关联清单。

LaTeX/PDF、图表和报告需真实生成、打开或渲染核对，不能只声称文件已经存在。
没有根据的引文、数值和“已证明”表述不能为改善行文而补入。
论文草稿不自动成为论文已完成或已发表的状态。

## 17. 备份、协作与公开发布

用户可选择项目的私有研究仓库，预先授权以已发布检查点为边界备份。
代码仓库与研究资产仓库分开；不把 SQLite 缓存、密钥和临时状态当成研究成果提交。
单写者起步；发现远程分歧暂停同步并报告，不自动合并权威研究 YAML。
备份完成以远程版本核对为准；还要能从克隆恢复合同、证据和检查点。

公开站点、公开仓库、论文投稿和向他人发送材料分别需要明确授权。
系统准备可审阅的公开清单和脱敏预览，默认保留私人原件。
用户授权过的固定私有备份策略不重复询问；改变访问范围或转为公开时重新决定。

## 18. 结题、归档与后续研究

用户可以结束一个阶段而继续项目，或归档整个项目。
系统保存成果清单、最后检查点、剩余问题、预算结算及恢复说明，标明是否还有实际运行的工作者。
将“已得到结果”“已通过某类验证”“已整理报告”“已公开发布”分别记录。
没有产出预期定理也可以归档，但应如实总结已做工作、失败依据和未完成原因。

几个月后重新打开项目，先展示当时目标、已知成果、未决义务、最后进展、可用预算与建议动作，
再按用户要求恢复，不依赖模型记住一段很长的旧对话。

## 走完整条旅程后的新增设计判断

原五角色主要解决单任务流程，还需补齐四项产品能力：

1. 项目管家：初始化工作区、连接诊断、多项目焦点、后台存活状态、归档与恢复。
2. 研究规划：把宽泛方向变成问题组合，管理周期目标、优先级与停滞后的决策建议。
3. 文献与新颖性：维护来源版本、定理适用条件、检索覆盖和原创性的不确定性。
4. 成果管理：精确成果清单、证据升级、报告/论文草稿、备份恢复与发布预览。

可先将项目管家放进入口角色，将成果管理放入结果角色；研究规划和文献能力按需成为
同一核心模型的专门角色。用户仍只面对一个研究助理，不手动串联角色。
新增角色不会获得自行扩大预算、认证数学正确性或公开发布的权限。

## 建议新增验收门槛

除了原 A1–A6，还应分别验证：新建空项目、导入部分失败、同名材料版本冲突、
跨项目隔离、后台退出/电脑睡眠后的正确状态、长期无进展、任务条件改变后的失效传播、
新文献推翻新颖性判断、条件性成果报告、从私有备份冷恢复、公开预览排除私人材料。

这些是后续范围建议，需进入明确开发计划后实施；不能因有本旅程文档就视为已经实现。
